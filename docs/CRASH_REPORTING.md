# Диагностика аварийных завершений

Ранняя автозагрузка `Diag` работает до Prefs и Net. На диск сразу записываются версия игры/движка, debug/release, ОС, CPU, GPU/API/драйвер, PID, контрольные точки перехода из хаба, запуска правил, первой отрисовки и смены фаз. `Logger` сохраняет ошибки ядра и скриптов с файлом, строкой и доступным стеком. Стеки GDScript включены также для release; переменные стека не захватываются.

Файлы — `user://logs/session-<время>-<PID>.log`, до 10 сеансов. Основной файл ограничен 2 МиБ и сохраняет начало. После лимита запись продолжается в `.log.tail` и `.log.tail.previous`, каждый до 128 КиБ. Ошибки также сразу записываются в `.log.errors` и `.log.errors.previous` с тем же пределом: обычные этапы не вытесняют последнюю ошибку. Каждый блок ограничен 16 000 символами; у слишком большого блока сохраняются начало и конец. Суммарно подробные файлы сеанса занимают до 2,5 МиБ. Отчёт объединяет эти части; старые части удаляются вместе с сеансом. Время — UTC и миллисекунды от старта.

Контекст принимает только известные поля и ожидаемые скалярные типы. Вложенный payload даже под ключом `phase`/`round_no` отвергается. Руки, ответы, сообщения чата, ключи API и аргументы действий не передаются в диагностику. Смена `party_game`, `game_id` или выход в лобби очищает сохранённую фазу/индексы до нового состояния; состояние с явно чужой игрой/партией отвергается. Пока нового состояния нет, остаётся текущая информация Net без старой фазы. Это исправляет вводящий в заблуждение контекст при переключении игр, но не исправляет доставку состояния старому UI.

Стандартный журнал Godot — отдельный источник: flush stdout и ротация 10 файлов. Для доступного файла сохраняется ограниченный снимок `.log.engine` при запуске, каждые 5 секунд и при штатном завершении. После перезапуска выбранный предыдущий журнал архивируется в этот же снимок, чтобы дальнейшая ротация не подменила его новым сеансом. До снимка последние строки при kill могут потеряться. В проверенном Godot 4.7.2 обработанный `--log-file` отсутствует в `OS.get_cmdline_args()`: произвольный внешний путь автоматически восстановить невозможно. Если путь не доступен, стандартный журнал отмечается отсутствующим, собственная диагностика и ошибки остаются. Старый файл по умолчанию не выбирается, если его время изменения предшествует старту текущего движка. Сопоставление стандартных файлов предполагает один процесс на профиль; одновременные процессы должны иметь отдельный APPDATA.

Фильтрация относится к контексту, а не к произвольному тексту стороннего `print` или сообщения движка: стандартный журнал и текст ошибок могут содержать то, что напечатал вызывающий код. Переменные стека не захватываются; неизвестные сетевые payload не сериализуются. Перед отправкой отчёта можно проверить его содержимое; автоматической отправки нет.

`user://running.flag` содержит JSON с PID, временем, путями журналов и последним этапом; обновляется через временный файл каждые 5 секунд и на контрольных точках. При штатном выходе удаляется. Принудительное завершение оставляет маркер, но само по себе не доказывает наличие программной ошибки.

После незавершённого запуска отдельный скрытый Windows PowerShell читает **Application Error, событие 1000** за соответствующий промежуток времени. Событие сопоставляется по PID, имени/пути приложения и, когда доступно, времени создания процесса. Для новых маркеров старт оценивается по часам движка, а не позднему `Diag._ready` после загрузки ресурсов; допуск сопоставления — 5 секунд. Это оценка, не дескриптор процесса Windows; при отсутствии времени создания защита от повторно использованного PID слабее. Результат — соседний `session-…-windows.json`: время события, модуль, путь модуля, код исключения и смещение. Системный журнал только читается; WER/реестр не меняются. Тайм-аут — 15 секунд по монотонным часам, не игровому `delta`; зависший собственный запрос завершается. Если основной поток игры завис, проверка тайм-аута сможет исполниться только после его возобновления. Нет события, недоступен PowerShell/журнал или отказано в доступе — в отчёте соответствующий статус, причина не выдумывается. При очень быстром повторном запуске Windows может ещё не успеть записать событие.

Кнопка «Скопировать лог» объединяет подробный журнал, стандартный журнал Godot и системные данные **того же сеанса**. В окне после вылета выбирается предыдущий запуск, в настройках — текущий. Большие журналы обрезаются с сохранением заголовка и конца. Отчёт никуда автоматически не отправляется.

Если процесс аварийно завершился до инициализации GDScript, Diag ещё не сможет создать маркер. Нативный стек движка/драйвера и дамп памяти не обещаются: здесь сохраняются доступные скриптовые стеки и запись Windows после перезапуска.

Экспорт `build/windows/PartyWorld.exe` версии 0.8.4 от 25.10.2026, проверенный координатором через `export-resource-probe.json`, ещё не содержит `hub/diagnostics.gd`/`diagnostic_logger.gd` от 26.10. Эти поля и улучшения не появятся в уже разосланном файле. Нужна отдельная разрешённая пересборка. Наблюдение «весь клиент завис, затем закрылся» не объясняется автоматически ошибкой GDScript: воспроизведённые ошибки старого UI при новом состоянии оставляли процессы живыми. Нового клиентского нативного дампа пока нет; штатный выход хоста не доказывает причину клиентского закрытия.

## Проверка

Все прогоны — с `--audio-driver Dummy` и отдельным `APPDATA` внутри `build/crash_logging_tests/`. Личный профиль и настройки звука игрока не менять.

- `--headless --path . --script res://tests/test_diagnostics.gd`: намеренная ошибка `%`, ошибка рабочего потока, контекст, отдельные отчёты старого/текущего сеанса, обрезка UTF-8, лимит и настоящий скрытый системный запрос. Две намеренные ошибки в логе ожидаемы; итог должен быть `ошибок=0`.
- `tests/test_windows_crash_info.ps1`: после предыдущего теста проверяет сформированный запрос на подставных событиях — разные PID/пути, шестнадцатеричный и десятичный PID, модуль/исключение, отсутствие события и отказ доступа. Системные события не создаются.
- С одним отдельным APPDATA три запуска `--headless --path . --script res://tests/diagnostics_recovery_probe.gd -- seed`, затем `-- verify`, затем `-- clean`. **seed принудительно завершает только собственный тестовый процесс**. Verify должен найти его последний этап и прежний PID, clean — не обнаружить ложный повторный вылет.
- Полная компиляция: `--headless --path . res://tools/_fuzz/compile.tscn`; смотреть журнал ошибок, а не только код выхода.
- `tests/test_diagnostics_followup.gd`: переполнение обоих ограниченных журналов, настоящие ошибки основного/рабочего потока, flush до close, сохранение контекста, смена игры/партии/лобби и типизация публичных полей, сохранность снимка стандартного лога, тайм-аут собственного тестового PowerShell при `delta=0`. Две ошибки с префиксом `ОЖИДАЕМАЯ_FOLLOWUP` намеренны.
- `pwsh -NoProfile -File tests/test_diagnostics_windows_followup.ps1`: после followup-теста — синтетические PID/пути/время создания при позднем `_ready`, found/empty/denied. Для ps1 без BOM нужен PowerShell 7 либо явное чтение UTF-8; Windows PowerShell 5.1 с `-File` может ошибочно прочитать кириллицу как ANSI. Исходные тесты для этого не изменяются.
- `diagnostics_followup_recovery_probe.gd -- seed`, `-- verify`, `-- clean`: отдельный общий профиль для трёх запусков; seed после переполнения завершает только себя, verify проверяет маркер/последнюю ошибку/стек/отчёт, clean — отсутствие ложного маркера после штатного выхода. По умолчанию проверяется также снимок стандартного лога. Отдельный свежий профиль и один повторно используемый `--log-file` с `DIAG_CUSTOM_LOG=1` проверяют честное отсутствие недоступного внешнего лога при сохранной собственной диагностике. Seed на Windows может вернуть код 0 даже при принудительном завершении; доказательство — оставшийся маркер и последующий verify, не один exit code.
- Копирование в системный буфер: `DIAG_TEST_CLIPBOARD=1` и test_diagnostics.gd без headless. Тест сохраняет и восстанавливает прежний буфер. В sandbox без доступа к clipboard эту отдельную проверку не запускать; состав отчёта проверяется и без него.

Для выпуска нужна новая сборка: уже разосланный `PartyWorld.exe` эти изменения не получит. Полный релиз этим изменением не создаётся.

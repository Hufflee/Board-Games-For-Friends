# Переход автообновления на полную сборку со сжатыми картами (0.9.1.2)

## Задача
- Установки с действующей версией **0.9.1 и новее** (полная 0.9.1/0.9.1.1 или exe 0.8.12 + патчи до 0.9.1+) —
  докачивают только недостающие патчи.
- Установки **0.8.12 … 0.9.0.8** (в т.ч. 0.8.121–0.9.0.8) — полную сборку со сжатыми картами Things in Rings,
  а не патч 0.9.1 на 435 МБ.

## Ограничение старого клиента
Клиент до 0.9.1.1 включительно (`update_client.gd` из exe 0.8.12 и из патчей 0.9.0.2–0.9.1.1) читает один
URL `releases/latest/download/latest.json` и решает так: база манифеста новее **версии exe** → zip, иначе —
цепочка патчей. У «exe 0.8.12 + патчи до 0.9.0.8» и «exe 0.8.12 + патчи до 0.9.1» версия exe одна и та же,
поэтому **одним манифестом старый клиент обе группы не разделит**:
- база 0.8.12 в манифесте → вторая группа получает патчи, но и первая качает патч 0.9.1 (435 МБ);
- база 0.9.1.2 → первая группа получает полную сборку, но и вторая тоже (вместо маленького патча).
Поле версии тоже не помогает: чтобы вторая группа увидела обновление, версия манифеста должна быть выше
0.9.1, а это видит и первая.

## Схема: два манифеста по очереди
Новый клиент (в патче и полной сборке 0.9.1.2) читает поля `full`, `patch_from`, `lines` и выбирает сам:
патчи — только если установленная цепочка совпадает с линией манифеста по SHA-256, все её звенья
подключены в этом запуске, файлы целы (SHA-256 на диске) и не надо качать патчи старее `patch_from`;
иначе — полная сборка.

1. **Переходный выпуск 0.9.1.2 (сейчас).** `latest.json`: база 0.8.12 и старая цепочка без изменений
   (те же файлы и суммы) + патч 0.9.1.2; `full` — `PartyWorld-0.9.1.2-Windows.zip`, `patch_from: 0.9.1`.
   - старый клиент на 0.9.1+ → только недостающие патчи (0.9.1.2, при нужде 0.9.1.1) и с ними новый клиент;
   - старый клиент на 0.8.12–0.9.0.8 → **по-прежнему цепочка с патчем 0.9.1** (обойти нельзя, см. выше).
     Им лучше скачать zip со страницы релиза вручную или дождаться шага 2;
   - новый клиент (кто уже на 0.9.1.2) → ничего не качает.
   Команды: `release.py patch 0.9.1.2 --allow-project`, `release.py full 0.9.1.2 --patch-from 0.9.1`,
   `release.py publish 0.9.1.2`.
2. **Финальный манифест — со следующим выпуском (0.9.1.3+), когда активные игроки прошли через 0.9.1.2.**
   `release.py finalize` → база манифеста = полная 0.9.1.2, старая линия 0.8.12 уходит в `lines`; затем
   обычные `patch V` (собирает патч для новой линии и `patch-V-from-0.8.12.pck` для старой) и `publish V`.
   - старый клиент на 0.8.12–0.9.0.8 → полная сборка 0.9.1.2, затем патчи новой линии;
   - новый клиент на exe 0.8.12 или полной 0.9.1/0.9.1.1 → только патчи своей линии;
   - **пропустивший переход** (старый клиент на 0.9.1/0.9.1.1) → полная сборка 0.9.1.2 (база манифеста новее
     его exe). Это цена ограничения: скачает больше, но получит рабочую сборку с откатом при сбое запуска.
